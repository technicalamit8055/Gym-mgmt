# Search engines and link previews: setup

The marketing pages (GymBook at `/` and SeatBook at `/library`) already
contain the code search engines need. This guide covers two things:

- getting the pages into Google and Bing;
- keeping them in good shape once they are indexed.

All the steps happen outside the code, apart from the environment variables
in step 1.

For how the pages are built, see "The marketing pages and search" in the
[README](../README.md#onboarding-how-a-gym-or-hall-joins). Briefly:

| What | Where |
| --- | --- |
| Every word on both pages: titles, descriptions, features, FAQ | [public/js/marketing.js](../public/js/marketing.js) |
| Head tags, JSON-LD, the crawlable copy, robots.txt, sitemap.xml | [src/marketing.js](../src/marketing.js) |
| Routes for `/`, `/library`, `/robots.txt`, `/sitemap.xml` | [src/routes/marketing.js](../src/routes/marketing.js) |
| Share images (1200×630) | `public/images/og/`, regenerated by `npm run og:gen` |
| Tests that guard all of the above | [tests/marketingSeo.test.js](../tests/marketingSeo.test.js) |

---

## 0. Choose the address you want indexed

Everything Google learns is tied to a hostname: rankings, links and history.
Moving hosts later is possible (see [Moving to a new domain](#moving-to-a-new-domain)),
but it costs weeks of reduced traffic.

If you plan to buy a real domain such as `gymbook.in`, do it **before**
step 3. A `*.duckdns.org` address works, but it looks less trustworthy in
search results and in WhatsApp previews. You also cannot add a `www` version
or set up email on it.

---

## 1. Server configuration

In the production `.env`:

```bash
ROOT_DOMAIN=slotify.duckdns.org   # the exact public hostname, no scheme or slash
TRUST_PROXY=true                  # nginx sits in front
TRIAL_DAYS=7                      # optional; the pages and FAQ show this number
```

**`ROOT_DOMAIN` is not optional for search.** It does two jobs:

- **Picks the canonical URL.** Every canonical URL, `og:url`, sitemap entry
  and JSON-LD `@id` becomes `https://$ROOT_DOMAIN/…`, whichever hostname the
  request arrived on.
- **Marks the platform's own root.** Without it, a three-part hostname such
  as `slotify.duckdns.org` is read as the gym `slotify`, the same way
  `acme.example.com` would be. The marketing pages, robots.txt and the
  sitemap are then never served there.

Restart after editing (`pm2 restart gymbook --update-env`).

### nginx

There should be one public address, served over HTTPS:

- **HTTP → HTTPS.** Certbot normally adds this redirect for you. Check it with
  `curl -sI http://slotify.duckdns.org/ | head -3`, which should show
  `301` and an `https://` `Location`.
- **`www` → the bare domain (real domain only).** Redirect one to the other
  with a 301, and set `ROOT_DOMAIN` to the one you keep:

  ```nginx
  server {
    listen 443 ssl;
    server_name www.gymbook.in;
    # ssl_certificate lines from certbot
    return 301 https://gymbook.in$request_uri;
  }
  ```

- **Don't cache HTML in nginx.** The app already sends `Cache-Control:
  no-cache` on the marketing pages.

## 2. Check it after deploying

Run these against production before telling any search engine about the site.
Each one should print what the comment says.

```bash
H=https://slotify.duckdns.org

curl -s $H/ | grep -o '<title>[^<]*</title>'
#  <title>Gym Management Software with WhatsApp &amp; UPI | GymBook</title>

curl -s $H/library | grep -o '<link rel="canonical"[^>]*>'
#  <link rel="canonical" href="https://slotify.duckdns.org/library" />
#  (https, and your ROOT_DOMAIN; if it says http:// or another host, revisit step 1)

curl -s $H/ | grep -c 'application/ld+json'
#  1

curl -s $H/robots.txt
#  User-agent: *  …  Disallow: /api/  …  Sitemap: https://slotify.duckdns.org/sitemap.xml
#  (plain text; if you see HTML, ROOT_DOMAIN is not being applied)

curl -s $H/sitemap.xml
#  <urlset …> with two <loc> entries: / and /library

curl -sI $H/images/og/gymbook.png | grep -i 'content-type'
#  content-type: image/png
```

If the title is the old generic "GymBook", the server is still running the
previous code. Your **browser** might show an old title even when curl is
correct. That is the service worker serving its cached copy, and it fixes
itself on the next load. Crawlers do not use service workers, so curl shows
what they see.

## 3. Google Search Console

<https://search.google.com/search-console>

1. **Add the site.** Pick one of the two property types.
   - **Domain property** (recommended). It covers http, https and every
     subdomain, and it is the only type the "Change of address" tool works
     with later. Google gives you a TXT record to add:
     - **DuckDNS:** in a browser, open
       `https://www.duckdns.org/update?domains=slotify&token=<your-duckdns-token>&txt=<the google-site-verification=… value>&verbose=true`
       It should answer `OK` and `UPDATED`. DuckDNS keeps one TXT value per
       domain, and the verification value has to stay in place.
     - **A real domain:** add the TXT record at your registrar or DNS host,
       with Name `@`.
   - **URL-prefix property** (no DNS access needed). Download Google's
     `google<code>.html` file and put it in `public/`. `express.static`
     serves it as `https://<host>/google<code>.html`. Commit it, deploy, then
     click **Verify**. Don't delete it afterwards: Google checks it again
     from time to time.
2. **Submit the sitemap.** Go to *Indexing → Sitemaps* and enter
   `sitemap.xml`. The status should change to **Success** with 2 discovered
   pages.
3. **Ask for the two pages to be crawled.** Use *URL Inspection*, paste
   `https://<host>/`, then **Request indexing**. Repeat for
   `https://<host>/library`. Click **Test live URL → View tested page →
   Screenshot** to see exactly what Googlebot rendered.
4. **Wait.** First indexing usually takes a few days, and a new site takes
   weeks to rank. *Performance → Search results* starts filling in after
   about a week.

## 4. Bing Webmaster Tools

<https://www.bing.com/webmasters>

Choose **Import from Google Search Console**. It copies the verified site and
its sitemap in one step. Several other search engines and AI assistants
draw on Bing's index, so this is worth the two minutes.

If you skip the import, add the site, verify it with the XML file or meta
tag method, then add `https://<host>/sitemap.xml` under *Sitemaps*.

## 5. Validate the structured data

- **Schema Markup Validator** (<https://validator.schema.org>): paste each
  URL. You should see `Organization`, `WebPage`, `SoftwareApplication` and
  `FAQPage` with **no errors**.
- **Rich Results Test** (<https://search.google.com/test/rich-results>):
  this one reports what Google will *display*. Two results are expected and
  are not problems:
  - **FAQ:** Google only shows FAQ rich results for well-known government
    and health sites, since 2023. The FAQ markup is still read by Bing and
    by AI answer engines, and it is accurate.
  - **Software App:** Google flags that `offers` plus `aggregateRating`
    or `review` are missing. They are left out on purpose: there is no public
    price yet, and there are no real ratings. **Never add invented ratings.**
    Google treats that as spam and can apply a manual action to the whole
    site.

When pricing goes public, add an `offers` entry to the `SoftwareApplication`
node in `structuredData()` in [src/marketing.js](../src/marketing.js). For
example: `{ '@type': 'Offer', price: '999', priceCurrency: 'INR' }`. Also
update the test that asserts `offers` is undefined.

## 6. Link previews (WhatsApp, Facebook, LinkedIn, X)

Most of your traffic will probably come from links shared in WhatsApp
groups, so check how the previews look:

| Where | How to check / refresh |
| --- | --- |
| Facebook, Instagram DMs | <https://developers.facebook.com/tools/debug/>: paste the URL and click **Scrape Again** after any change |
| LinkedIn | <https://www.linkedin.com/post-inspector/> |
| WhatsApp | No tool. It caches a preview per exact URL, so to see a change, send yourself the link with a new query string (`/?v=2`) |
| X / Twitter | The old card validator is gone. Paste the link into a draft post |

Each should show the 1200×630 card, the page title and the description.

---

## 7. Speed

Test `/` and `/library` on **mobile** at <https://pagespeed.web.dev>. Search
ranking uses the field data (real Chrome users), which appears once the site
has enough traffic. Until then, the lab score is a guide.

If a score drops, the usual causes are:

- a large new image without `width` and `height`, which causes layout shift;
- a new script loaded in the `<head>`, which blocks rendering.

## Changing the words on the pages

Everything is in [public/js/marketing.js](../public/js/marketing.js). The
server and the browser both read it, so the visible page, the crawlable
copy and the JSON-LD always match.

1. **Edit the content.** Keep within these limits; the tests fail otherwise:
   - `title` at most **60** characters, or Google cuts it off;
   - `description` at most **160** characters.
2. **Make sure every FAQ answer is true** today. Google can penalise
   structured data that misstates the product.
3. **Regenerate the share images** if you changed a `name`, `headline` or
   `lede`: run `npm run og:gen`. This needs Chrome or Edge installed. Commit
   the PNGs.
4. **Run `npm test`.**
5. **Bump `VERSION` in [public/sw.js](../public/sw.js)** if you changed any
   file under `public/js/`. Returning visitors then get the new page in one
   go, instead of a mix of old cached files and new ones.
6. **Deploy, and request re-indexing** of the changed page in Search Console
   (step 3.3).

Choose words for searchers, not for the team. People search for "gym
management software", "gym billing software with WhatsApp" and "library
seat booking software". They don't search for product names they haven't
heard of yet.

## Adding another page

An example would be a free "gym membership price calculator" page, which can
attract search traffic of its own.

1. Add its content to `marketingContent()` (or a sibling export) in
   `public/js/marketing.js`.
2. Add a route next to `/` and `/library` in
   [src/routes/marketing.js](../src/routes/marketing.js), guarded by
   `onPlatformRoot(req)`.
3. Add its path to the sitemap. `sitemapXml()` currently lists
   `MARKETING_PATHS`.
4. Add a test like the `/library` one in `tests/marketingSeo.test.js`.
5. Link to it from the footer of both pages. A page nothing links to is
   slow to be found and ranks poorly.

## Moving to a new domain

1. **Point both hostnames at the server.** Set `ROOT_DOMAIN` to the new one,
   and add the new hostname to nginx and certbot.
2. **Redirect the old hostname** with a 301 that keeps the path:
   `return 301 https://newdomain$request_uri;`. Keep it in place for at
   least a year. The installed member apps (`--server https://slotify.duckdns.org`)
   also depend on the old host, so rebuild the APK before you ever remove it.
3. **Add the new domain** to Search Console as a Domain property.
4. **Use *Settings → Change of address*** on the old property to tell Google
   about the move.
5. **Submit the new `sitemap.xml`.** Repeat steps 3–4 in Bing as well.

## After launch

Weekly for the first month, then monthly:

- **Search Console → Pages.** Both URLs should be **Indexed**. "Crawled –
  currently not indexed" is normal for the first week or so.
- **Search Console → Performance.** Check which queries bring impressions.
  If a query gets impressions but no clicks, rework the title and
  description to answer it.
- **Search Console → Enhancements.** There should be no errors.
- **Links from other sites** do more for a new site than anything on the
  page:
  - listings on software directories (Capterra, G2, SoftwareSuggest,
    Techjockey);
  - a link from every gym's own website;
  - a short post in gym-owner and study-hall-owner communities.

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `robots.txt` or `sitemap.xml` returns the app's HTML | `ROOT_DOMAIN` is unset or doesn't match the hostname exactly, so the host is read as a gym (step 1) |
| Canonical URL says `http://` or the wrong host | `ROOT_DOMAIN` is unset, and `TRUST_PROXY` is unset behind nginx |
| Search Console: "Duplicate, Google chose different canonical" | Two hostnames serve the page. Add the 301 redirects in step 1 |
| Search Console: "Blocked by robots.txt" on a `/api/…` URL | Expected. API responses are not pages |
| WhatsApp preview shows the old title or image | WhatsApp's per-URL cache; test with `?v=2` (step 6) |
| Browser tab shows the old title but curl is right | The service worker's cached copy; it updates on the next load |
| `npm run og:gen` fails to find a browser | Install Chrome or Edge; the script tries both before Playwright's own Chromium |
